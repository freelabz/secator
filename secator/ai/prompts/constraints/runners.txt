<truncated_output>
A long SHELL output is capped: the middle is dropped and replaced by a `…(truncated N chars)…` marker (the head and tail are kept). The dropped part is NOT saved anywhere — to get it, RE-RUN the command in a narrower, filtered form: pipe it through grep / sed / head / tail / jq / wc -l INSIDE the command so only what you need comes back.

<example>
Shell output truncated:
```
{"task":"shell","status":"success","count":1,"results":"HTTP/1.1 200 OK\nServer: Apache/2.4.41\n…(truncated 8291 chars)…\n</html>"}
```
Follow-up actions (re-run with a filter, NOT a file path):
```
run_shell(command="curl -sI https://target/ | grep -i 'set-cookie'")
run_shell(command="curl -s https://target/ | grep -iE 'error|warning|denied'")
```
</example>
</truncated_output>


<file_io>
Write any files you generate (e.g. a markdown report) to the runner folder's outputs directory: $workspace_path/.outputs/. Prefer this location; reading or writing files elsewhere requires user approval.
The results of a task/workflow you just ran are returned to you directly in its tool result — read them THERE. Do NOT re-run query_workspace just to see what a run you launched produced (it is already in the tool result) — UNLESS that result is INCOMPLETE (it was item-capped; the tool result then carries a scope_note with the runner's `runner_id`/`runner_type`), in which case read the rest with a query scoped to that runner: query_workspace(query={"_context.<runner_type>_id": "<runner_id>"}) (add `_type`/filters to narrow; see <queries>). Use query_workspace only to read findings that are NOT in your current tool results — e.g. findings from earlier/other runs — or to obtain a finding's stable `_uuid` (required by mark_vuln_*/update_finding), since the run tool result omits it. It is the single source of truth and the only supported way to read the workspace. Do NOT read local report files (e.g. via cat/jq) to look up findings.
</file_io>
