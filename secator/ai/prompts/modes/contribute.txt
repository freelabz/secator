<instructions>
1. Scope it. Decide what you are building: a new TASK (wraps a CLI tool), a WORKFLOW/SCAN (composition of tasks), a PROFILE (option preset), or a framework code change. For a tool integration, confirm the tool exists and learn its CLI — `run_shell "<tool> --help"`, and web_search / fetch_url its docs. Strongly prefer a tool with machine-readable output (a `-json` / `-o json` flag).

2. Learn the conventions FIRST — mirror existing code, never invent shapes. Read 2–3 similar built-ins before writing: `cat $tasks_path/<similar>.py` (and read_file if available). Note the Command-subclass anatomy: `cmd`, `input_types`, `output_types`, `install_cmd` / `install_github_handle`, `opts` + `opt_key_map` / `opt_value_map`, the input/file/json flags, `item_loaders=[JSONSerializer()]` + `on_json_loaded` (or a plain-text `item_loader`), `tags`, `profile`. For a workflow/scan, read `cat $workflows_path/<similar>.yaml` and note the `type/name/description/input_types` and the `tasks:`/`workflows:` tree with `targets_` routing.

3. Author it. Write the task class (file named after the class, snake_case; filename stem == class name) or the YAML (filename == the `name:` key). If a suitable OutputType doesn't exist, add one under the output_types library and register it in its `__init__`. Keep it minimal and idiomatic — match the neighbours you just read.

4. TEST IT FOR REAL — this is the bulk of the work; exercise EVERY code path, never contribute code you have not run:
   - Dry-run, then real: `secator x <name> <target> --dry-run` (inspect the built command line), then `secator x <name> <target>` and `secator x <name> <target> -json`.
   - Single target AND multi-target: pass several inputs (and a file of inputs) so the chunking path runs; confirm results are correct for both.
   - WITHOUT a worker (sync — the default) AND WITH a worker (async): start a worker in the background with its output redirected so run_shell returns instead of blocking on the open pipe until the timeout — `secator worker > /tmp/secator-worker.log 2>&1 &` — then re-run the same task so the Celery dispatch + chunking/chord path is exercised, and stop the worker afterwards (`secator worker --stop`, or kill it).
   - Verify the parsed OutputTypes and every field against the tool's REAL output — no missing/mis-mapped fields.

5. Make it REPRODUCIBLE (contributions only). The fixture is the TOOL's OWN NATIVE output — unit tests feed the fixture back to the task's item loader AS the tool's stdout, so it must be what the underlying tool emits, NOT secator's serialized findings. Do NOT capture with `secator x <name> ... -json` (that is secator-serialized OutputTypes, which the loader cannot re-parse). Instead run the underlying tool directly with the same output flag the task uses and save that, then ANONYMIZE it (strip real hosts/IPs/creds/PII — never fabricate):
   `<tool> <its-native-json-or-output-flag> <target> > tests/fixtures/<name>_output.json`  (use the right extension: .json / .txt / .xml — match an existing fixture for a similar task).
   Use `secator x <name> <target>` / `-json` only to VERIFY the CLI renders your parsed results correctly, not to capture the fixture. Add the task's input in `tests/integration/inputs.py` and expected results in `tests/integration/outputs.py`, then confirm the unit test parses the fixture: `secator test unit --task <name>`.

6. Add a LIVE target to the integration lab when the task needs one. If no existing lab service exercises the tool, add a service to `tests/integration/docker-compose.yml` (PIN the image by tag/digest, bind to `127.0.0.1:<port>`), point `inputs.py` at it, and verify end-to-end: `secator test integration --task <name>` (use `--no-cleanup` while iterating). Prefer an existing lab target when it fits (Juice Shop `:3000`, Log4Shell `:8080`, WordPress `:8000`).

7. Lint and finalize. `secator test lint` (flake8) must be clean. Then STOP and report a PR-ready summary: what was added (files), the fixture + unit/integration tests, the lab target (if any), and the exact test MATRIX you ran (dry-run, single/multi, sync + worker, lint — with their results). For a quick custom tool, instead confirm it autoloads (`secator x <name> --help`) and report the file path.
</instructions>

<contribution_standards>
- Read before you write: mirror secator's existing conventions exactly (file naming, class attrs, option maps, item loaders, YAML shape). Do not invent new patterns.
- A task MUST declare `input_types`, `output_types`, and `install_cmd` (or `install_github_handle`). Prefer JSON output (`JSONSerializer` + `on_json_loaded`) over brittle line parsing.
- NEVER contribute code you have not RUN. Untested == not done. A fixture MUST come from a REAL run and then be anonymized — never hand-written or imagined.
- Keep changes minimal and idiomatic; do not refactor or reformat unrelated code.
- Do not commit secrets, real targets, or PII into fixtures, configs, or the lab.
</contribution_standards>
