<instructions>
1. Scope + learn the tool. Decide what you are building (a TASK wrapping a CLI tool, a WORKFLOW/SCAN composition, a PROFILE, or a framework change). For a tool integration, confirm the tool exists and learn its CLI — `run_shell "<tool> --help"` and web_search / fetch_url its docs. Strongly prefer a tool with machine-readable output (a `-json` / `-o json` flag).

2. Learn the conventions FIRST — mirror existing code, never invent shapes. Find the installed secator (above) and read 2–3 similar built-ins: `cat <pkg>/tasks/<similar>.py` for a task — note the Command anatomy: `cmd`, `input_types`, `output_types`, `install_cmd` / `install_github_handle`, `opts` + `opt_key_map` / `opt_value_map`, the input/file/json flags, `item_loaders=[JSONSerializer()]` + `on_json_loaded` (or a plain-text `item_loader`), `tags`, `profile`. For a workflow/scan read `cat <pkg>/configs/workflows/<similar>.yaml` (the `type/name/description/input_types` and the `tasks:`/`workflows:` tree with `targets_` routing).

3. Author + VALIDATE it live. Write the task class (file named after the class, snake_case; stem == class name) or the YAML (filename == the `name:` key); add a new OutputType only if none fits. Drop it in the templates dir so it loads, then exercise EVERY path — never ship code you have not run:
   - `secator x <name> <target> --dry-run` (inspect the built command), then `secator x <name> <target>`, then `secator x <name> <target> -json`.
   - single target AND multi-target (and a file of inputs) so the chunking path runs; confirm both.
   - WITHOUT a worker (sync — the default) AND WITH one: `secator worker > /tmp/secator-worker.log 2>&1 &` (redirect so run_shell returns instead of blocking on the pipe), re-run the task so the Celery dispatch + chunking/chord path runs, then stop it.
   - Verify every parsed OutputType field against the tool's REAL output — nothing missing or mis-mapped.

4. Make a REPRODUCIBLE fixture. The fixture is the TOOL's OWN NATIVE output — unit tests feed it back to the item loader AS the tool's stdout, so it must be what the underlying tool emits, NOT `secator x ... -json` (that is secator-serialized findings the loader can't re-parse). Run the underlying tool with its own output flag and save it (`<tool> <native-json-or-output-flag> <target> > <name>_output.json`, matching an existing fixture's extension), then ANONYMIZE it. Also prepare the test wiring to ship: the unit fixture (`tests/fixtures/<name>_output.<ext>`) and the `tests/integration/inputs.py` + `outputs.py` entries.

5. Lab + integration. If the task needs a live target, stand one up (prefer a small service) and validate against it; for the repo's integration suite, add a service to `tests/integration/docker-compose.yml` (pin the image, bind `127.0.0.1:<port>`) or reuse an existing lab (Juice Shop `:3000`, Log4Shell `:8080`, WordPress `:8000`). When you HAVE the git checkout (a LOCAL run), run `secator test unit --task <name>`, `secator test integration --task <name>` and `secator test lint`. In a sandbox you do NOT have that suite — produce the files and state that the repo tests + lint still need to be run.

6. TOO BIG TO TEST HERE → try lighter first, THEN hand off (never fake it). If standing up the lab or running the tool hits a run_shell memory warning (a "Memory limit … exceeded" line — run_shell kills the process when it blows the environment's memory cap), it's too heavy to run as-is here. FIRST try a lighter approach when one exists — a leaner lab image / a single smaller service instead of a full stack, a reduced dataset or scope, fewer threads/concurrency, a minimal repro — and re-validate. Only if it STILL cannot fit (a genuinely heavyweight tool or lab, e.g. large Java tooling) do you hand off: deliver the files you have PLUS the exact lab recipe and test commands, and ask the user to validate on their own machine. NEVER fabricate a result you could not actually obtain.

7. Deliver per <deliverable>, then summarise: what you built, the test MATRIX you actually ran (and anything you could not run + why), the fixture + unit/integration test wiring, and the lab target.
</instructions>

- NEVER ship code you have not RUN. Untested == not done. A fixture MUST come from a REAL run, then be anonymized — never hand-written or imagined.
- SECURITY — a contribution may become PUBLIC. NEVER put confidential or organizational information into ANY file you produce (task code, YAML, fixtures, lab definitions, inputs/outputs): no real workspace / org / user data, no internal hostnames / IPs / targets, no credentials / tokens / API keys, no PII. Use placeholder/example targets and the public lab services only, and anonymize every fixture.
- Keep changes minimal and idiomatic; do not touch unrelated code.
</contribution_standards>
